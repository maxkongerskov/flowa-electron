# FLOWA — code audit, 2026-10-20

Scope: the whole app at `~/Projects/Flowa-Electron` (Electron 1.2.1, ~5k lines of real source, excluding `vendor/whisper.cpp`).
Method: full read of every source file, plus targeted experiments to confirm or refute suspicions. Nothing was modified.

Baseline checks run: `vitest run` → **126/126 passing**, 13 files. `tsc --noEmit` on both node and web projects → **clean**. Working tree clean at `a0f9596`.

Each finding is marked **[verified]** (proven by reading the code, often with an executed experiment) or **[plausible]** (logic checks out but needs a runtime reproduction).

---

## High

### 1. In-app updates on Windows and Linux have no code-signature check [verified]

Anyone who can publish to the GitHub release feed can run arbitrary code on every Windows and Linux install.

- `electron-builder.yml:57` — the `win:` block has no `publisherName` and no signing certificate. `scripts/build-release.sh:8` even documents it: *"Windows: x64 NSIS installer (unsigned; electron-updater still installs it)"*.
- The shipped feed config confirms what that means. `release/win-unpacked/resources/app-update.yml` is exactly:
  ```
  owner: maxkongerskov
  repo: flowa-electron
  provider: github
  updaterCacheDirName: flowa-updater
  ```
- electron-updater treats a missing `publisherName` as "signature OK" (`node_modules/electron-updater/out/NsisUpdater.js:85`): `if (publisherName == null) return null`.
- The install path never looks at signatures, only that the feed lists a file with the expected extension (`src/shared/updates.ts:295-305`). The sha512 is read from the same feed, so it is not an independent trust anchor.
- `src/main/updates.ts:133` then runs `quitAndInstall(true, true)` — silent NSIS install.

**Trigger:** a leaked release token, a compromised account, or a bad CI secret. Upload a new `latest.yml` plus an `.exe`. The user clicks Download once; the payload runs silently. No certificate error, no publisher mismatch, no Gatekeeper prompt for an unsigned NSIS run out of the updater cache. Linux AppImage/deb is identical.

**macOS is correctly protected** — `src/shared/updates.ts:263-277` only permits auto-install for Developer ID-signed builds, and Squirrel.Mac enforces the same identity independently. So this is a Windows/Linux-only exposure.

## Medium

### 2. Modifier-only shortcuts fire on ordinary modifier-plus-mouse gestures [verified]

Holding Shift (or Right Alt) and releasing it after a **mouse** gesture starts dictation.

- `native/macos/flowa-helper.swift:111-115` observes only `flagsChanged`, `keyDown`, `keyUp` — no mouse events.
- `src/shared/shortcut.ts:333` fires on release when `state.armed && !state.chord`, and `chord` is only ever set by a keyboard event (`shortcut.ts:314-317`).
- `Shift`, `Control` and `Alt` alone are all accepted shortcuts (`shortcut.ts:28-34,153-156`).

**Trigger:** with Shift bound, hold it and drag-select text, then release. No `key` event occurred, so `chord` stays false and dictation starts. The Flow Bar appears and the mic opens without the dictation key being tapped. Same for Right Alt + a click.

### 3. The Flow Bar renderer owns all microphone capture, and nothing recovers if it dies [verified]

- `src/main/windows.ts:63` — the bar window is created hidden at launch and never destroyed, precisely because *"the bar's renderer also owns microphone capture"*.
- There is **no** `render-process-gone`, `unresponsive`, or reload handler anywhere in the project (grepped).
- Every dictation goes through `FlowBar.start()` → `request('capture:start', …)` → `win.webContents.send`. If that renderer crashed, every send is a no-op, every request resolves its 15 s fallback, and the user gets "Couldn't start recording. Check your microphone and try again." forever.

**Trigger:** a renderer crash (OOM, GPU driver fault, a bad Web Audio call). **Observable:** dictation is permanently dead until the app is restarted, with an error message that blames the microphone.

### 4. A slow capture start leaves the microphone live forever and bricks recording [verified]

- `src/main/windows.ts:133-137` — `start()` waits 15 s, then resolves `{ok:false}` and drops the pending entry.
- The renderer side keeps going regardless: `AudioCapture.start()` sets `this.isRecording = true` at line 111 and never stops the stream.
- The later `bar:reply` finds no pending entry (`windows.ts:105-112`) and is discarded.

**Trigger:** `getUserMedia` / `AudioContext` takes longer than 15 s — a device held exclusively by another app, a permission prompt left on screen, a slow Bluetooth handshake. **Observable:** the macOS mic indicator stays on indefinitely, and every later dictation fails immediately at `AudioCapture.start():44` with `throw new Error('Already recording')`. The only recovery is restarting the app.

### 5. The fn watcher loses key state across a disabled event tap [verified]

- `flowa-helper.swift:76-82` — on `tapDisabledByTimeout` / `tapDisabledByUserInput` it re-enables the tap and returns, but never resyncs the module-level `fnDown` (declared at line 28) or `modifierDown` (line 29).
- The app only clears its own `fnDown` on an `fn-up` (`src/main/hotkey.ts:108`).

**Trigger:** fn held when the tap is disabled — heavy system load past the tap timeout, screen lock/sleep, a TCC prompt, or Input Monitoring toggled in System Settings. **Observable:** the `fn-up` is lost and the helper still believes fn is down, so the *next* physical press emits nothing (guarded by `!fnDown`) and only its release emits `fn-up`. The first tap after the event silently does nothing. With a modifier shortcut, the stale `armed`/`down` state can make an unrelated later release start dictation.

Related: when re-enabling fails — which is what `tapDisabledByUserInput` usually means, i.e. the user just removed Input Monitoring — the helper emits **nothing**, not even `denied` (line 77). The app keeps `isAuthorized === true` and the "isn't active yet" banner never appears.

### 6. The shortcut recorder can leave the global hotkey suspended indefinitely [verified]

- `src/renderer/src/components/ShortcutField.tsx:64-81` suspends the hotkey on entering the recorder and only resumes on Escape, Cancel, a successful save, or effect cleanup.
- Closing the main window does not unmount the component — `src/main/index.ts:62-68` intercepts `close` and merely hides the window.

**Trigger:** open the recorder (Change), then close the window or switch away and forget it. **Observable:** `hotkey.suspended` stays `true`, and every press of the dictation shortcut is ignored until the app restarts. There is no `blur` / visibilitychange handler to catch this.

### 7. A corrupt `prefs.json` silently resets every setting, on every launch [verified]

- `src/main/store.ts:13-38` — a parse failure becomes `raw = null`, `coercePrefs(null)` yields all defaults, and the bad file is **not** rewritten (the rewrite branch requires `raw` to be a parseable object at line 27).
- `src/main/paths.ts:58-63` — `writeFileAtomic` never `fsync`s before or after the rename.

**Trigger:** crash or power loss during a prefs write, or a hand-edited/truncated file. **Observable:** language, microphone, max duration, speech model, hardware, onboarding and first-run state all revert to defaults, the shortcut drops back to `fn`/`F8`, no error is shown, and it repeats every launch until the user finds and deletes the file.

### 8. `fetch-model.mjs` renames the download into place *before* hashing it [verified]

- `scripts/fetch-model.mjs:58-60` — `fs.renameSync(partial, dest)` happens, then line 63 hashes `dest` and exits 1 on mismatch.
- The skip condition at line 43 is `else if (!fs.existsSync(dest))`.

**Trigger:** a truncated or corrupted response, or a changed file upstream. **Observable:** a bad `models/ggml-large-v3-turbo.bin` is left in place; every later `npm run setup:model` skips the download because the file exists, and every release build fails its preflight (`build-release.sh:49`) until the file is deleted by hand. The in-app downloader is **not** affected — `transcriber.ts:369-373` hashes the `.partial` before renaming.

### 9. `release.sh` pushes the tag before building [verified]

- `scripts/release.sh:71-76` — commit, tag, `git push origin "v$NEW"`, *then* build.
- The guard at lines 50-61 aborts when the tag already exists locally or on origin.

**Trigger:** notarization, signing or any build step fails after the push — the most likely failure points are exactly downstream. **Observable:** the version is committed and tagged on origin with no GitHub Release and no feed entry. Retrying aborts ("Tag v1.2.1 already exists on origin"); retrying with `patch` leaves 1.2.1 permanently unreleased. Recovery needs a manual `git push origin :refs/tags/vX.Y.Z`.

### 10. `publish-release.sh` can overwrite an already-published release [verified]

- `scripts/publish-release.sh:39-44` — if the tag exists it runs `gh release upload --clobber` plus `gh release edit --latest` on **every** file in `$OUT`.
- It never checks notarization or stapling, and `build-release.sh:31-38` produces signed-but-unnotarized DMGs whenever `FLOWA_REQUIRE_NOTARY` is unset.
- It globs whatever is in `release/` without checking filenames contain `$VERSION` (lines 19-31).

**Trigger:** run `build-release.sh` without `FLOWA_REQUIRE_NOTARY=1`, then `publish-release.sh`; or publish against an existing tag with a stale artifact in `release/`. **Observable:** every installed client's `latest.yml` / `latest-mac.yml` is swapped immediately, a non-notarized DMG becomes the public download, and a stale extra artifact is uploaded and listed. `release.sh` sets `FLOWA_REQUIRE_NOTARY=1`, so it cannot hit this — only the standalone script can.

### 11. macOS bundles ship without `app-update.yml` — in-app update may fail there [plausible]

Verified fact: `release/mac-arm64/Flowa.app/Contents/Resources/app-update.yml` does not exist, while the Windows and Linux bundles both have one. `src/main/updates.ts:196-235` relies on electron-updater's config-on-disk for the download helper (`AppUpdater.js:545-548` reads `updaterCacheDirName` from it). `setFeedURL` (`updates.ts:206`) may bypass it for the *check* but probably not for the download.

**How to settle it:** run "Check for updates" on the installed 1.2.1 mac build with a newer release published. One run decides it.

## Verified clean — checked specifically, no defect found

Worth stating, because these are the things that look alarming and aren't:

- **Audio never leaves the machine.** The only network calls in `src/` are the Hugging Face model download, GitHub release metadata, and `127.0.0.1` inference. Confirmed by grepping every `fetch` / `http` / `WebSocket` site.
- **No shell-string execution anywhere.** `proc.ts:22` is `spawn(command, args)` with no `shell: true`; PowerShell gets UTF-16LE base64 (`psArgs`); the frontmost PID reaches the helper via argv and is parsed as `Int32`; AppleScript app-name interpolation in `textInserter.ts:146` is escaped.
- **Semver comparison is correct** — 1.2.10 > 1.2.9, prerelease ordering right, unparseable versions compare equal so they can never trigger a downgrade.
- **Update URL checks are solid** — `isFlowaReleaseUrl` requires https + `github.com` + repo prefix, and dot-segments normalize before the prefix test, so `.../flowa-electron/../../x` cannot pass.
- **macOS auto-install is correctly gated** on Developer ID signing; ad-hoc builds only ever get the public installer link.
- **`useAppState` is correct** — revision guard rejects stale snapshots, subscription registered before the snapshot request, listener and `alive` flag cleaned up.
- **`recent.json` is bounded** at 100 entries; decode is tolerant of bad entries.
- **Atomic-rename writes** cannot produce a torn live file (durability is finding 7, not tearing).
- **`sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`** on both windows; navigation denied and new windows denied-with-external-open in `hardenWebContents`.
